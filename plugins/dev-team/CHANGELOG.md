## 0.9.0 (2026-10-25)

Part 1 of 0.9, the parts that do not wait on the unlazy trial's verdict (owner's go, 2026-10-24). Runnable lane ledgers and the three-way bake-off wait for OS Flow's verdict after its second runnable-ledger lane.

- **CI decides.** Where the app's `CLAUDE.md` names CI (`CI: <required checks>` and how to read them), the approver reads CI itself from GitHub for the exact reviewed head sha and approves only when every named check concluded `success` there. Failed, cancelled, pending, missing, skipped, or green only on another sha is red; when CI and the local gate disagree, CI wins; when it cannot read CI it escalates. The gate-runner reports CI beside its local numbers. An app with no CI line keeps the local gate (approver, gate-runner, loop page "CI decides").
- **Every review states its coverage.** Each Review-stage report ends with `Coverage: head <sha>; checked: <...>; not checked: <... and why, or none>` (reviewer, spec-auditor, security-reviewer, critic, and the design team's design-auditor). The approver reads every line against `git diff --name-only`: a report with no line or on another head did not pass, and a changed path no code-reading review (reviewer, spec-auditor, security-reviewer) checked is ESCALATE, naming the path.
- **Tests named are tests run.** Any command that names tests (a filter, a file list, a list of names) reports how many it named and how many ran; fewer ran than named is red even when every test that ran passed and the marker printed. From OS Flow's unlazy trial lane 1 (2026-10-21), where a `-t` filter matched one of its two named tests (gate-runner, owner, loop page).
- **Raw checks at the owner's go.** The approval file carries a Raw checks section: each command the approver ran and its output as printed. The owner gives the go from it, and a row's evidence that no raw block shows is not evidence.
- New eval cases, 3 runs each: `approver-ci-binding` (CI's e2e failed on the reviewed head while every report and the local gate say green: ESCALATE naming e2e, raw CI output shown, main unmoved) 3 of 3; `approver-coverage-gap` (a changed path no code-reading review checked: ESCALATE naming it) 3 of 3; `gate-runner-test-count` (a lane check that ran 1 of its 2 named tests: reported 1 of 2 and red, no test renamed) 3 of 3. ## 0.7.0 (2026-10-12)

Ideas from three outside sources, read at pinned commits and rewritten in this team's voice: obra/superpowers (bb92a77), garrytan/gstack (70fab3e) and forrestchang/andrej-karpathy-skills (2c60614). Scope approved by the owner on 2026-10-12. What was taken and from where is in `THIRD_PARTY.md`; what was looked at and not taken is in `skills/REJECTED.md`.

- **A fix round closes with verdicts.** Each source re-checks its fixed findings by id with `fixed` (and the `path:line` or run that shows it) or `not fixed`; "attempted" is not fixed. Each lists new breakage in the fix diff as new findings. Before the re-checks the reviewer sorts the fix diff: a behavior, test or build change outside the fixed findings' paths gets a full pass from the reviewer and the security-reviewer in the same round; a docs-only change keeps the reviews (loop page, Limits on fixing; reviewer, spec-auditor, security-reviewer).
- **Four more ways to lower the bar**, in `no-quiet-lowering` (now nine moves): acceptance text rewritten to meet the work (`acceptance edited`, the original line still checked, only the owner accepts the new text), product code that branches on a test or CI signal, a snapshot regenerated without its test changing, and proof of a weaker kind than the claim. The spec-auditor builds rows from the spec as it stood at the branch point and preloads the skill.
- **Declined to judge.** The reviewer and the spec-auditor list every behavior they set aside as outside the spec, with the reason; the combined findings file gathers them and the architect rules on each before the fix round (a row, or "not required" in the memory file). The approver checks every line has a ruling. Findings are graded by what a person using the app gets, not by whether the spec names the input.
- **Plans name their blind spots and seams.** `slice-the-plan` adds an Interfaces line per lane (consumes and produces, by exact name and signature, spelled the same across lanes) and a Review Focus section (up to five inputs or failure modes the spec implies that no red test covers, each pinned by a new red test in the owning lane); every Review-stage brief carries the list. The lane-table header is unchanged.
- **Clean start, full report.** A lane runs the unit suite in its new worktree before the first edit; a red baseline holds it with `blocked-by:`. `tests-first` runs the whole suite and names every red seen, even one the lane did not cause; names the app change that would make a test fail before writing its body; and mocks carry the full data shape.
- **Security findings need evidence.** A supported finding has an attacker-controlled entry point, a boundary crossed, the impact shown and the defenses checked; anything less is a hypothesis listed apart. A supported finding is searched for at every sibling entry point, and the report opens with complete, partial or not assessed.
- **Simple and surgical** for the owner and the fixer: every changed line traces to the brief or the finding; no unasked features or abstractions; nearby code is not improved or restyled; dead code they did not make is reported, not deleted.
- **Skill descriptions say when to use the skill, not what it does**, for all fourteen skills (superpowers found agents follow a summarized workflow in the description and skip the body).
- Eval `root-cause-red-first`: `green-after-fix` no longer needs the blank line unittest prints between `Ran N tests` and `OK`. A 0.6.0 full-suite run fixed the bug and ran the suite green, but piped the output through `grep`, which drops that line, so the check failed a correct run. The check now accepts one or more line breaks there, needs `OK` as a whole word, and no longer counts `Ran 0 tests`. Checked offline on 13 kept traces (all still pass), a grep-piped copy (now passes), and copies that end red, run zero tests, print `OKAY`, or go green only before the source edit (all fail).
- Evals: two new cases, regex and tool use only, each checked offline first against good and bad hand-made outputs. `reverify-fix-round` (the reviewer as a subagent after a fix round where C1 is truly fixed, C2 only attempted and the same commit cuts the tax rate outside both findings' paths: R1 fixed, R2 not fixed, C2 left open, C1 `fixed <sha>`, the tax change a new finding R3, nothing edited). `lowering-moves` (a branch that loosened an acceptance line with its test, returns early under `CI`, and regenerated a snapshot without its test, beside one honest helper: the three named with paths, at least major, the helper not a hit). First live round: `lowering-moves` 3 of 3; `reverify-fix-round` 2 of 3, the miss a correct run that wrote its verdicts as yes and no in the verified-fixed table, so the reviewer's text now names the verdicts there and the graders accept that form.
- Full suite on 0.7.0, 3 runs each, main sessions on sonnet, Claude Code 2.1.296: 54 of 54 (18 cases), $11.67.

## 0.6.0 (2026-10-11)

The review loop runs its reviewers at once, merges their findings into one list, caps fixing at two rounds, and ends with an approver. Scope approved by the owner on 2026-10-11, after comparing this loop with a published "software factory" loop (spec writer, builder, four parallel reviews, wait for all, at most two fix rounds, an approver that merges or escalates). Eleven roles, fourteen skills, fifteen stages.

- Loop (`workflows/milestone-loop.md`): Spec check, Black-box check, Design check and Review (old stages 7 to 10) become one **Review** stage (7): the spec-auditor, the critic, the design team's design-auditor (only when screens change), the security-reviewer and the reviewer run at the same time, each as its own subagent with no shared context, on the same head. The reviewer still writes its hypotheses before it reads any other report or any builder's account; the critic stays screen-only. New **Combine findings** (8): nothing moves until every report is filed, then the reviewer, after its own review, builds one table the fixer, the approver and the checks read: `| ID | Severity | Source | Finding | Where | Kind | Status |`, ids `C<N>`, one row per finding with every source and its id, the highest severity when sources disagree, ranked blocker, major, minor, and `disputed: <why>` for a finding the code contradicts (back to its source, never to the fixer). New **Approve** (11) before **Owner go** (12). Watch is now stage 14.
- **Kind** column in the combined table: `behavior` (the fix changes what the code does; every security finding; the default when unsure) or `surface` (copy, labels, i18n keys, styling, layout, docs). It picks the fixer's first model: a `behavior` row runs the fixer on `opus` from the first attempt, a `surface` row on `sonnet` with the 0.5.2 step-up. From the fixer bake-off (`evals/ROUTING.md`, Bake-offs): on a finding whose review prescribed the wrong fix, opus fixed the real cause 3 of 3 and sonnet 0 of 3; on copy and naming findings they matched and sonnet cost about a fifth.
- **An exception is not a fix.** Turning a ruling test (banned terms, a duplicate set, a form-file map, an exceptions table) green by adding an exception, an allow-list or baseline entry, or narrowing the rule counts as a failed repair unless the architect signed off the rule change in the memory file; the fixer stops and asks instead, and the reviewer checks for it when it re-verifies. Both models did this in the bake-off (opus 3 runs, sonnet 2). A review's prescribed fix is still the fixer's to root-cause.
- The architect stays on `opus`, confirmed by the plan bake-off (`evals/ROUTING.md`, Bake-offs): recall level (0.46 against 0.48), head-to-head opus 7, sonnet 4, 1 tie, at $2.39 against $0.84 a plan. Open for the next retro: 3 of 24 plans used the exact lane-table header.
- Security review in every loop: the `security-reviewer` existed but no stage called it; it now runs in every milestone's Review stage, on `opus`.
- **Limits on fixing**, one table in place of three overlapping rules: two attempts per finding (sonnet, then opus with the first's cause line and diff; the 0.5.2 step-up), two fix rounds per milestone (a round is the fixer on every open row, the gate, then each source re-checking its fixed findings by id; after round 2 any open blocker or major goes to the owner), and the same root cause twice for gates, lane builds and reviews outside a fix round. A finding never gets a third attempt.
- New role **`approver`** (`opus`, tools Read, Glob, Grep, Bash, Write; read-only on code): reads every Review-stage report, the combined table, the gate numbers and the release checklist, checks the head and the diff itself, and writes `APPROVE` or `ESCALATE` with a reason in a fixed decision table plus a checks table, in `<milestone>-approval.md`. It never fixes. With auto-merge off an APPROVE goes to the owner for the go.
- **Auto-merge**, a per-project option, off by default (owner's decision of 2026-10-11). On only when the app's `CLAUDE.md` has `Auto-merge: safe changes` and a line saying whether merging to main deploys; either missing means off. The approver may merge only if every check passed this round (gate green on the reviewed head, every review passed, no open finding, every release-checklist line true), the change is under the `CLAUDE.md`'s line limit (default 400 changed lines), it is a two-way door, it touches no contract file, auth, money, schema or migration, secret, live sending or publishing, deploy config or always-ask path, and merging does not deploy unless the `CLAUDE.md` allows it. It re-checks the reviewed head, merges, and confirms with `git merge-base --is-ancestor`; anything else escalates. Sending, spending, publishing and live data stay the owner's whatever the setting. The full policy lives in `agents/approver.md`.
- `release-checklist`: read by the approver and signed by the owner; merge danger gains a size line and a protected-paths line (from `git diff`, never a lane's report); the merge-gate lines also cover a merge the approver makes. The gate-runner still never merges.
- Roles: `reviewer` (runs in parallel, hypotheses before any other report, builds and keeps the combined table), `security-reviewer`, `spec-auditor` and `critic` (run in the Review stage in their own context; re-check their own fixed findings; the spec-auditor's Missing row counts as a blocker, Partial or High gap as a major), `fixer` (works the combined table's open rows only; the two-attempt and two-round limits), `gate-runner` (the checklist is the approver's input). "Never merge" stays true for every role but the approver under the policy.
- `skills/REJECTED.md`: the automatic-merge row keeps merging by default, the reviewer merging and unattended merging rejected, and records the new position (opt-in per project, default off, with these limits, by the owner's decision of 2026-10-11). The CI-budget bypass stays rejected.
